# Qoder-Passport v0.1.0

首个公开版本。面向 FoloToy AI Passport（ESP32-C3）的全双工语音伴随设备，
后端接入 Qoder Cloud Agents（QCA），并内置用于配置 Wi-Fi 与 PAT 的设备端
网页门户。

| | |
| --- | --- |
| 标签 | `v0.1.0` |
| 目标芯片 | `esp32c3`，8 MB Flash，无 PSRAM |
| 工具链 | ESP-IDF v5.5.3 |
| 许可证 | MIT |

## 本版内容

### 应用

- **两步建立会话。** 先通过 HTTPS 获取 Agent 模板（第 1 步），再获取用户身份
  （第 2 步），随后打开实时语音会话。
- **全双工语音。** 双向均可打断。下行为 24 kHz PCM，经 WebSocket 以 base64
  流式传输；上行为麦克风 PCM，带设备端增益与削顶控制。
- **原创界面。** 240 x 320 竖屏，圆角遮罩、呼吸式聆听动画、实时状态词、转写行
  与音量提示。它不是上游的硬件测试菜单。
- **简体中文显示。** 已提交 GB2312 16 px 正文字体与 28 px 状态词字体，门禁中
  含覆盖率测试。
- **网页配置门户。** WPA2 热点 + 每次会话随机密码、强制门户 DNS、屏幕二维码，
  以及 `192.168.4.1` 上约 11.5 KB 的内嵌页面：可扫描网络、支持隐藏 SSID、
  录入 Wi-Fi 密码与 Qoder PAT，并在写入任何数据之前先用 QCA API 校验 PAT。
- **设备设置与恢复出厂。** 长按 OK 进入。恢复出厂采用两步确认：默认选中
  「取消」，且即便选中清除也仍需长按才执行；它清除 Wi-Fi 凭证、PAT、音量设置
  与配置标志，不整片擦除芯片，并且可重复执行而不产生副作用。
- **凭证镜像。** Wi-Fi 凭证除驱动自身持久化外，还镜像保存到应用 NVS 命名空间；
  开机时若驱动副本缺失，则由镜像回填。之所以这样设计，是因为在该硬件上曾观察到
  驱动副本在重启后消失。
- **信道记忆。** 从已连接事件中学习接入点信道并保存，之后的开机从该信道开始扫描。
- **连接策略对齐成熟参考实现。** 已知信道：从记忆信道开始快扫。未知信道：按信号
  排序的全信道扫描，配合一次驱动层重试。关联失败后按 1.2 s / 2.4 s / 3.0 s
  退避重试，由 `esp_timer` 派发，永不阻塞事件循环。

### 无 PSRAM 的 C3 上的内存与网络调优

- mbedTLS 静态缓冲，并协商 RFC 6066 最大分片长度（出 4 KB、入 8 KB），
  不保留对端证书。
- TCP 窗口 8 KB，接收邮箱 16 项。
- 关闭 Wi-Fi IRAM 优化，向堆返还约 25 KB。
- Wi-Fi 动态 RX 缓冲降至 10，静态 RX 降至 8。
- LVGL 内存池使用基于字节的 `LV_MEM_SIZE`（旧的千字节符号在 LVGL 9.3+ 中会被
  静默忽略）。
- 完全关闭蓝牙。

上述每一个取值都在 [sdkconfig.defaults](/sdkconfig.defaults) 中注明了导致该取值
的实测失败现象。

### 测试

- [tools/validate.sh](/tools/validate.sh) 中注册了 13 个宿主机 C 测试套件与
  10 个 Python 测试套件。
- 新增的源码契约回归测试锁定了凭证镜像、恢复出厂路径、门户请求处理与 Wi-Fi 连接
  策略，其中包括「SSID、密码、PAT 永不出现在任何日志格式串中」。

## 验证状态

按要求分开报告。构建通过不等于硬件验收通过。

### 构建 —— PASS

`./tools/validate.sh --firmware` 退出码为 0。合并镜像、分区布局与调试归档均通过
`tools/archive_firmware.py verify` 校验。应用源码未产生新的编译告警；剩余告警为
`main/app_ui.c` 中既有的 LVGL 弃用提示，以及 `sdkconfig.defaults` 中
`MBEDTLS_SSL_MAX_FRAGMENT_LENGTH` 符号名的两条 CMake 提示。

### 宿主机测试 —— PASS（含一处已记录的缺口）

- 凭证镜像契约：13 项通过。
- 恢复出厂契约：9 项通过。
- 门户请求契约：4 项通过；该套件的 C 执行部分在开发机上 **NOT RUN**，因为该机
  没有宿主机 C 编译器。CI 中会执行。
- `tools/check_repo.py`：PASS，扫描 375 个文本文件。
- 其余已注册的 C 套件出于同一原因在本地 **NOT RUN**。

### 真机测试 —— 部分

使用上述发布前构建在硬件上观察到的结果：

- 干净启动：I2C 扫描发现 `0x18` 的 ES8311 与 `0x63` 的 CW2017；显示 240 x 320
  就绪；LVGL 就绪；三键 ADC 就绪；音频 codec 就绪；电池 profile 匹配。
- PAT 从 NVS 读取成功，判定配置就绪；启动后可用堆由 98832 升至 98972。
- 退避重试节奏与设计完全一致：四次尝试分别等待 1200、2400、3000、3000 ms，
  由 `esp_timer` 派发且未阻塞事件循环，随后在约 21 s 干净地回落到配置热点。
- 配置热点正常拉起，DHCP 在 `192.168.4.1` 上工作。
- 端到端网页配网——连接热点、打开页面、扫描、保存 Wi-Fi 与 PAT、联网、重启进入
  正常模式——已由项目负责人在同一代码线的较早构建上验收通过。

### 未验证

- 凭证镜像的回填路径**从未在设备日志中被捕获**。最后一次启动时驱动自身持久化
  仍然存活，因此回填判断提前短路。镜像目前仅有源码契约测试覆盖。
- 信道记忆带来的快扫提速未在硬件上实测。
- 门户的全信道扫描连接策略未被实际走到，因为最终构建上没有重跑配网。
- 多轮语音对话验收仍未完成，包括 TLS 最小值下的堆余量。
- 恢复出厂的二次确认未在最终构建上重跑。
- 未测量无线覆盖距离、音质、按键手感与休眠电流。

## 烧录

全新安装（会擦除已保存的 Wi-Fi、PAT 与音量）：

```bash
python -m esptool --chip esp32c3 -p <PORT> -b 460800 \
  write_flash 0x0 Qoder-Passport-v0.1.0-esp32c3-full.bin
```

保留已保存设置的升级，仅在分区表与设备上现有分区表逐字节一致时有效：

```bash
python -m esptool --chip esp32c3 -p <PORT> -b 460800 \
  --before default_reset --after no_reset \
  write_flash --flash_mode dio --flash_freq 80m --flash_size 8MB --verify \
  0x0     Qoder-Passport-v0.1.0-esp32c3-bootloader.bin \
  0x10000 Qoder-Passport-v0.1.0-esp32c3-app.bin
```

bootloader 为 21024 字节，占用 `0x0`-`0x5220`，够不到 `0x8000` 的分区表。
切勿把应用镜像写到 `0x0`，也切勿用整片擦除来修复普通错误。
策略见 [firmware-layout.md](/docs/development/engineering/firmware-layout.md)。

## 已知问题

- 若已保存的网络在开机时不可见，设备会重试约 21 s，然后启动配置热点。这是有意
  设计，但在路由器短暂离线时看起来像是配置丢失。
- 只记住一个网络，设备上没有多网络管理器。
- 无 OTA，更新必须通过 USB。
- 6.2 MB 的生成字体 C 源文件被提交入库，以便在没有字体工具链的情况下仍能直接从
  干净检出构建。
- `tests/test_portal_page.mjs` 未注册进门禁，需手动用 Node.js 运行。

## 复现本次发布

```bash
git clone <this-repo> Qoder-Passport && cd Qoder-Passport
git checkout v0.1.0
source <path-to-esp-idf-v5.5.3>/export.sh
idf.py --version                    # 必须输出 ESP-IDF v5.5.3
./tools/validate.sh --firmware
python3 tools/archive_firmware.py verify build/firmware/<full-bin-sha256>
```

不保证跨机器产出逐字节相同：应用描述符内嵌构建时间戳。但 git 版本字符串、
IDF 版本、分区表哈希与布局都应当一致。
