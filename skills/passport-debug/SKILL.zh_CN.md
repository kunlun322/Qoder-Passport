# 诊断固件故障

确定受影响工作区，阅读 `AGENTS.md`，先执行 `git status --short --branch`。
明确用户要求解释还是修复：诊断不授权编辑、重新构建、烧录或推送。
日志可能来自另一份固件，当前工作区不自动等于对应源码。

## 建立证据

- 记录现象、可复现的用户操作、最早相关错误、复位／异常类型、任务、固件
  版本及日志中的 ELF SHA。只索取会改变结论的缺失信息，不索取凭据、设备
  二维码原文或整份私有环境信息。
- 区分观察事实、可能原因与待验证推测。栈指针超出日志给出的任务栈边界，
  是栈异常的直接证据；准确的分配／调用函数仍需要匹配符号。
- 分析当前应用代码时阅读相关头文件和实现。针对现象查询
  `docs/hardware-design/AI_HARDWARE_DEVELOPMENT_GUIDE.zh_CN.md`，不套用
  通用 ESP32 开发板的引脚或假设。

## 先匹配符号，再解码地址

对于保留的门禁构建，运行
`python3 tools/archive_firmware.py verify <archive-directory>` 验证归档，
将崩溃／启动日志的 ELF 身份与清单的 `app_elf_sha256` 对比。截断哈希必须
唯一匹配一个候选；存在歧义时索取完整身份。其他构建需要取得产生已烧录镜像
的 ELF 及身份依据。相近 Git 版本或之后重新构建的文件不能替代。

匹配后才用已激活工具链的
`riscv32-esp-elf-addr2line -pfiaC -e <matching.elf> <addresses>` 解码异常 PC、
返回地址及可信调用帧。原始栈里的数字不全是返回地址。缺少符号时，说明仅从
日志能够确认什么，并索取匹配产物；不编造源码文件／行号，不把当前源码的
重新构建冒充旧固件。

## 缩小原因范围

按相关路径检查：任务栈／局部缓冲及调用深度、分配失败与最大可用连续堆块、
UI 线程／字体／样式、外设初始化，或页面退出后仍存活的任务／回调。中文
问题阅读 `docs/development/engineering/lvgl-chinese-fonts.zh_CN.md`。不通过
隐藏占位符掩盖缺字，不关闭看门狗／栈保护，也不在未评估无 PSRAM 内存预算
时盲目增加所有缓冲／任务栈。

仅诊断时，添加探针、重新编译或硬件实验是建议的下一步，不代表已授权修复。
用户要求修复后，实施有证据的最小修改，补回归测试，按正常流程构建并交接
真机测试。区分模拟／主机测试与真实硬件结果。

## 给出可行动的结论

说明已观察故障、有证据的原因及置信程度、未知项，以及最小下一步检查或
已授权修复。实际修复后分别报告 `Build`、`Host tests`、`Device tests` 与
`Unverified`。进展需要真实固件、设备访问或新用户决定时停止，不改无关代码，
不反复运行没有新信息的实验。
