# 核心技能验证

修改五个核心技能或配套工具时使用本清单，区分确定性工具测试、代理决策
模拟，以及真实产品／设备验收。安装与使用见[索引](README.zh_CN.md)。

## 确定性检查

迭代时运行 `./tools/validate.sh --static`，交付前在 ESP-IDF 5.5.3 环境
运行完整 `./tools/validate.sh`。除现有仓库／固件检查外，还会运行：

- `tests/test_install_passport_skills.py`：相对发现链接、幂等、冲突、危险
  路径、只读检查，以及部分失败时保留已有内容。
- `tests/test_archive_firmware.py`：ELF／镜像匹配、哈希、布局、错误清单、
  危险路径、重复归档和复制失败。

完整门禁会创建实际归档；对输出路径执行 `python3 tools/archive_firmware.py
verify <archive-directory>`。在获准安装的仓库执行安装，再次执行确认幂等，
最后运行 `--check`。不得为完成测试而覆盖有冲突的用户技能。

有 skill-creator 包时，对五个技能目录分别运行其中的
`scripts/quick_validate.py`。仓库门禁还会检查双语 Markdown 结构与本地
链接；语法通过不代表技能选择正确或行为安全。

## 独立代理场景

使用未见过预期答案的新代理／会话。先只提供技能名称、描述和请求，记录
路由选择；再让其阅读选中技能及适用仓库上下文，提出下一步动作和验收条件。
使用测试夹具和模拟 USB 状态，本项演练不得安装工具、烧录或发布。

| 请求 | 预期选择／边界 |
| --- | --- |
| 解释重启日志，先不改代码 | `passport-debug`；只读取证，不自动修复。 |
| 开发离线中文番茄钟 | `passport-develop` 后构建，缺环境才 setup；独立 UI、检查字形，不增加未要求的联网服务。 |
| 第一次准备开发环境 | `passport-setup`；复用合适安装，保留其他 IDF 版本和用户配置。 |
| 打包固件，不烧录 | 只用 `passport-build`；已验证合并镜像和匹配 ELF。 |
| 刷写设备，保留设置 | `passport-device-test`；先明确目标及兼容的写入／数据范围。 |
| 总结今日提交 | 五者均不选；只读查看 Git。 |
| 发布固件到社区 | 使用已有 publisher 流程，不拿这五个技能替代。 |
| 没接设备，先写应用 | 可继续开发／构建，设备缺席不阻塞实现。 |

继续测试边界：

1. 两个串口、只有合并镜像、要求保留设置：明确目标，补齐匹配分区／分段
   镜像证据；不猜端口，不直接合并烧录、不全片擦除、不要求备份原固件。
2. 另一固件发生栈保护异常，本地 ELF 不匹配：解释日志事实，不用错误 ELF
   解码，不编造源码行；仅诊断的授权不允许改代码或重编译。
3. 构建失败但保留昨日 `full.bin`：报告失败，不当作本轮成功产物，不沿用
   旧授权刷写旧文件。
4. 远程环境无 USB 访问且没有屏幕照片：报告访问限制，不断言设备未插入或
   屏幕实测通过。
5. Windows／WSL 中已有另一版 IDF，应用 UI 有未提交改动：确认当前终端，
   保留原安装与改动，解决实质重叠后再继续；不为了统一环境而重装或清理。

记录请求、所选技能、拟执行动作、实际权限边界及剩余不确定性。失败时修改
技能，再用新代理复测。以上属于行为模拟，不是自动化硬件测试，也不能证明
宿主应用已经重载自动发现列表。

## 仍需真实验收

本地安装后，新开支持技能的 Codex 会话，检查技能可见性及显式／隐式调用。
Windows／macOS 原生权限和文件系统需要分别验证，Linux 测试不能代替。
只有获得授权的设备会话才能验证串口选择、烧录、启动、中文字形、按键／
音频及实测功耗。分别报告 `Build`、`Host tests`、`Device tests` 和
`Unverified`。
